## 0. 给 AI 助手的必读说明

在动手改任何代码之前，请按这个顺序读：

1. **`README.md`** —— 了解项目**现在是什么样**（架构、接口、已知限制）
2. **本文档** —— 了解项目**要变成什么样**（目标、验收标准、约束）

几条硬性要求：

- **本文档的「3. 目标能力清单」是需求的唯一来源。** 如果你的改动不服务于其中任何一条，先停下来问清楚，不要自作主张加功能。
- **不要跳阶段。** 阶段之间是有依赖的（尤其阶段 2 必须早于阶段 3），理由写在「5. 硬性约束」里。
- **每完成一项，回来更新「2. 现状基线」里的实测数字，并勾选对应条目。** 这份文档如果和代码脱节，就失去意义了。
- **不要照搬对标项目的量化数字**（89.4% / 0.911 / 71.7%）。它们是特定语料 + 特定标注集下的结果，本节「5. 硬性约束」有详细说明。

## 1. 项目最终目标

**一句话**：构建一个面向复杂**长任务**的多 Agent 执行框架，解决单 Agent 在长链路中「任务拆解不清、执行偏离、上下文膨胀、缺少测试验收、中断后难恢复」的问题。

**能力边界**：围绕六个方向构建可扩展的 Agent —— 任务规划、子任务执行、质量门禁验收、RAG 检索、记忆沉淀、工具治理。

**与当前版本的根本差别**：现在的实现只能**产出文本**；目标形态要能**真的动手做事**——写文件、跑测试、调外部工具，并且全过程可追踪、可中断、可恢复。

### 对标参照

| 项 | 内容 |
| --- | --- |
| 参照项目 | AgentsTemplate（https://github.com/Mruser95/AgentsTemplate.git），2026.02–2026.05，约 4 个月 |
| 参照技术栈 | LangGraph、LlamaIndex、BM25、RRF、AutoMerging、Rerank、Milvus、FastAPI、SQLite、MCP、Docker |
| 参照成果 | 见「3. 目标能力清单」各条的目标值 |

**定位说明**：参照项目是**学习与对标目标**，用于明确「一个完整形态长什么样」。本项目要做出**同等的工程能力**，而不是复制它的领域内容（法律文档）与具体数字。

## 2. 现状基线（baseline）

> 这一节必须保持与代码一致。每次完成一项能力后，回来更新实测值。

### 已实现

| 能力 | 实现方式 | 实测 |
| --- | --- | --- |
| 多 Agent 协作 | 3 角色：Manager / Worker / Checker（+ summarize 节点） | 最小链路 `finished` |
| 状态机编排 | LangGraph 0.2.60 StateGraph + 条件边 | 一条主线 + 一个重试回环 |
| 混合检索 | BM25（中文单字+双字）+ 向量 + RRF（k=60） | top 3 注入 Prompt |
| 向量库 | ChromaDB（主）/ 本地 JSON（降级） | 后端 `chromadb` |
| Embedding | 本地哈希向量，384 维 | 零依赖，可离线 |
| 切分 | 固定 500 字递归切分，overlap 80 | 20 篇 → **51 chunk** |
| 断点续跑 | `SqliteSaver` + `thread_id` | 可读回完整状态 |
| 流式输出 | SSE：`start` / `node` / `done` / `error` | 节点级事件 |
| 服务 | FastAPI，8 个接口 | — |
| 部署 | Docker Compose | 启动时自动建索引 |
| 容错降级 | 8 处降级/兜底策略 | CI 的 `degraded` 任务验证其中 2 条 |
| 测试 | pytest 19 用例，全离线 | 约 1 秒跑完 |
| CI | GitHub Actions，全量依赖 + 降级路径双任务 | — |

### 关键短板（对应目标清单的差距）

- **Worker 没有任何工具** —— 不能读写文件、不能执行命令，只能产出文本
- **`deps` 字段不参与调度** —— 子任务按 `current_index` 顺序执行，`deps` 只用于把依赖结果注入 Prompt
- **没有评测集** —— 无法回答「检索效果提升了多少」
- **没有 token 计量** —— 成本不可见，上下文未做压缩
- **无 workspace 隔离** —— 所有任务共用 `data/` 目录
- **无 Tester** —— 只有 LLM 判定的 Checker，没有真实的测试执行

## 3. 目标能力清单

七个子模块。每条给出**目标 → 验收标准 → 现状差距**。验收标准写成可判定的形式，能落成测试用例的就直接写出来。

### M1 · 任务规划与 DAG 调度

**目标**：以 `plan.json` 作为任务状态的**唯一事实来源**，按 DAG 拓扑依赖调度子任务，而不是按数组顺序。

| 验收标准 | 当前状态 |
| --- | --- |
| 计划落盘为 `workspace/<thread_id>/plan.json`，进程重启后可重新加载并继续 | ❌ 计划只存在 LangGraph state 里 |
| 每个子任务有明确状态：`pending` / `ready` / `running` / `done` / `failed` | ❌ 只有 `current_index` 下标 |
| 调度器按**拓扑序**选取就绪节点 | ❌ 按 `current_index` 顺序 |
| 无依赖关系的同层子任务**并行执行** | ❌ 全串行 |
| 测试：构造 `A→C`、`B→C` 的图，断言 A、B 同批调度，C 等待两者完成 | ❌ |
| 测试：某分支失败时，其它无依赖分支仍能正常完成 | ❌ |

**差距**：中等。改动集中在 `graph/state.py` + `graph/workflow.py` + `agents/manager.py`。
⚠️ **注意**：状态结构变更会导致**旧 checkpoint 不兼容**，升级时需要处理（或直接清空 `data/checkpoint.sqlite`）。

---

### M2 · 多角色分工（3 → 7）

**目标**：从 3 个角色扩展到 7 个，让「规划 / 执行 / 测试 / 验收」各司其职。

参照项目的角色划分是 `Manager / Coder / Checker / Tester / ...`。建议的落地划分：

| 角色 | 职责 |
| --- | --- |
| **Manager** | 任务规划，产出 `plan.json`；最终汇总 |
| **Coder** | 实际写文件、改代码（**需要 M6 的工具层**） |
| **Tester** | 运行测试、解析结果、把失败信息回灌给 Coder |
| **Checker** | 验收交付物是否满足验收标准（现有角色） |
| **Retriever** | 独立的检索角色（可选，也可以保持 Worker 内嵌调用） |
| **Summarizer** | 上下文压缩与记忆沉淀（对应 M5） |
| **Reflector** | 失败复盘，产出改进建议（可选，优先级最低） |

| 验收标准 | 当前状态 |
| --- | --- |
| 每个角色有独立 Prompt、独立 node、明确的输入输出契约 | ❌ 仅 3 个 |
| 角色之间不越权（Coder 不自我验收，Tester 不改代码） | ⚠️ 部分（Worker / Checker 已分离） |
| 测试：能构造一条「Coder 写 → Tester 测 → 失败 → Coder 修 → Tester 通过」的完整内循环 | ❌ |

**差距**：大。**强依赖 M6**——没有工具层，Coder / Tester 无从执行。

---

### M3 · 质量门禁（规划 — 执行 — 测试 — 验收 闭环）

**目标**：验收不再只靠 LLM 判断，而是接入**真实可执行的门禁**。

| 验收标准 | 当前状态 |
| --- | --- |
| Tester 能真实运行测试命令并解析通过/失败 | ❌ |
| 测试失败的错误输出回灌给 Coder 触发修复（内循环） | ❌ |
| 文件写入后自动执行 lint gate（Python / JS / Go 等多语言） | ❌ |
| 门禁不通过时不允许进入下一阶段 | ⚠️ Checker 有打回，但无真实门禁 |
| 内循环有次数上限，防止 Coder–Tester 无限循环 | ❌ |

**差距**：大。优先级高于 M2 的其它角色。

---

### M4 · RAG 检索链路

**目标**：从「平铺切分 + 两路召回」升级为「层级切分 + 自动合并 + 精排」的完整链路。

| 验收标准 | 当前状态 |
| --- | --- |
| **有评测集**：N 条人工标注 query（建议 ≥ 30），脚本输出 Hit@1 / Hit@3 / MRR@5 | ❌ **【最高优先级】** |
| 有可复现的**基线数字**，且每次调参后能对比 | ❌ |
| 层级切分保留文档结构（父 / 子节点关系） | ❌ 固定 500 字平铺 |
| AutoMerging：命中叶节点后返回合并后的父节点 | ❌ |
| Cross-Encoder Rerank 接在 RRF 之后精排 | ❌ |
| 语料换成真实领域文档，规模上一个量级（千级 chunk） | ❌ 20 篇自建文档 / 51 chunk |
| 向量库支持切换（Milvus 作为可选后端） | ⚠️ 仅 Chroma / JSON |

**参照项目的做法**（供参考，不要照搬）：
- 语料：21 部法律文档 → 4,372 个 leaf chunk
- 切分：按「编 / 章 / 节 / 条」拆解法律层级，条文做 1024 / 256 **二级 Hierarchical 切分**
- 检索：Milvus HNSW + BM25 + RRF + AutoMerging + Cross-Encoder Rerank
- 评测：47 条人工标注 query，Hit@1 80.9% → 89.4%，MRR@5 0.911

**差距**：大。**但顺序很重要**——必须先有评测集，再做其它优化。

---

### M5 · 记忆沉淀与上下文治理

**目标**：长任务下控制上下文膨胀，用压缩代替原文透传。

| 验收标准 | 当前状态 |
| --- | --- |
| 有 token 计量：能看到每个节点的输入 / 输出 token 数 | ❌ |
| 已完成子任务在 Prompt 中以**摘要**形式出现，而非原文 | ❌ 原文透传 |
| 超长任务的单轮上下文相对现状有**可测量的下降**，并记录压缩率 | ❌ |
| 短期记忆压缩：距离当前较远的执行记录被降级为摘要 | ❌ |
| 有后台调度器按「任务长度 / 难度 / 所需 skills」分级派发 | ❌ |

**参照项目的做法**：设计 COLLATOR 后台调度器，统一调度长/短/难度/skills 任务；平均单轮上下文由 **53k tokens 降至 15k tokens，下降 71.7%**。

**差距**：大。依赖 M1（有稳定的计划结构才谈得上压缩）。

---

### M6 · 工具治理

**目标**：让 Agent 能真的操作文件系统与执行命令，同时**把越权风险关在笼子里**。

| 验收标准 | 当前状态 |
| --- | --- |
| 所有工具经**统一注册表**暴露，模型只能调用注册过的工具 | ❌ **完全没有工具** |
| 文件操作被限制在 `workspace/<thread_id>/` 内 | ❌ |
| **路径穿越测试**：`../../etc/passwd` 一类的输入必须被拒绝 | ❌ |
| 命令执行有白名单 + 超时 + 输出截断 | ❌ |
| 危险操作有风险校验（删除、覆盖、写系统目录） | ❌ |
| 相对路径约束：所有路径必须显式相对 workspace 根 | ❌ |
| 支持通过 **MCP** 接入外部工具 | ❌ |

**参照项目的做法**：统一封装工具调用，施加提示限制、边界风险校验、相对路径约束与多语言 lint gate，规避越权文件操作风险。

**差距**：**最大**。这是整个项目的关键路径，也是唯一一块**没有现成库、需要自己设计工程决策**的部分。

⚠️ **M6 必须在 M1 的 workspace 隔离完成之后才能做**，否则开放写权限有真实的数据风险。

---

### M7 · 工程化交付

**目标**：多任务互不干扰，可并行、可观测、可一键部署。

| 验收标准 | 当前状态 |
| --- | --- |
| 每个 `thread` 有独立的 `workspace` 与 `SessionDB` | ⚠️ 仅隔离 LangGraph state |
| 任务计划 / 执行记录 / 文件产物 / 虚拟环境完全独立 | ❌ |
| 测试：并发跑多个任务，产物不互相污染 | ❌ |
| SSE 事件覆盖工具级：`tool` / `tool_start` / `tool_end` | ❌ 目前 4 种节点级事件 |
| 支持多用户并行执行 | ❌ |
| 可观测性：traceId + metrics 端点 | ❌ |
| Docker Compose 一键部署 | ✅ |

**差距**：中。

## 4. 分阶段实施路线

> 排序原则：**先做「能度量」，再做「能执行」。** 跳过度量直接堆功能，会陷入无法判断改动好坏的困境。

### 阶段 1 · 建立度量能力　`前置：无`

| 交付物 | 验收 |
| --- | --- |
| `eval/queries.jsonl` 人工标注集（≥ 30 条） | 每条含 query + 期望命中的 chunk id |
| `eval/run_eval.py` | 输出 Hit@1 / Hit@3 / MRR@5；支持多组参数对比 |
| 基线报告 | 记录当前切分与检索参数下的指标 |

- 标注必须**人工完成**。用 AI 标答案 = 自证，指标失去意义。
- 这一步产出的第一组数字，是全项目后续所有优化的判断依据。

### 阶段 2 · 检索效果提升　`前置：阶段 1`

| 交付物 | 验收 |
| --- | --- |
| `rag/rerank.py` Cross-Encoder 精排 | 接在 RRF 之后；指标相对基线有提升且可复现 |
| 检索参数对比表 | 至少覆盖 `RRF_K`、`CHUNK_SIZE`、embedding 后端 |

### 阶段 3 · 计划与调度　`前置：阶段 1`

| 交付物 | 验收 |
| --- | --- |
| `graph/plan.py`：plan schema + 拓扑排序 + 就绪集 | 通过 M1 全部验收标准 |
| `app/workspace.py`：`thread_id → 目录` + 路径校验 | 路径穿越测试通过 |
| `plan.json` 落盘与重载 | 重启后能继续执行 |

### 阶段 4 · 工具化执行　`前置：阶段 3（必须）`

| 交付物 | 验收 |
| --- | --- |
| `agent_tools/registry.py` 工具注册表 | 通过 M6 全部验收标准 |
| `agent_tools/file_ops.py` 文件工具 | 路径穿越、越权写入测试通过 |
| `agent_tools/shell.py` 命令工具 | 白名单 + 超时 + 截断 |
| `agents/coder.py` / `agents/tester.py` | 通过 M2、M3 验收标准；能完成「写 → 测 → 失败 → 修 → 通过」内循环 |

> 目录名用 `agent_tools/` 而非 `tools/`——`tools/` 已被命令行脚本占用。

### 阶段 5 · 记忆与上下文治理　`前置：阶段 3`

| 交付物 | 验收 |
| --- | --- |
| token 计量 | 每个节点能看到 token 消耗 |
| 历史摘要压缩 | 长任务单轮上下文可测量下降 |
| 后台调度器 | 按任务长度/难度分级派发 |

### 阶段 6 · 工程化收尾　`前置：阶段 4`

| 交付物 | 验收 |
| --- | --- |
| workspace / SessionDB 隔离 | 并发任务互不污染 |
| SSE 工具级事件 | `tool_start` / `tool_end` |
| MCP 接入 | 能挂载至少一个外部工具 |
| Web 前端（可选） | 节点时间线 + 子任务卡片 + markdown 渲染 |
| 可观测性 | traceId + metrics 端点 |

## 5. 硬性约束（不要做的事）

这些是从实际踩坑中总结出来的，请严格遵守：

1. **不要把参照项目的领域方案硬套到本项目语料上。**
   「编 / 章 / 节 / 条」是**法律文档**特有的结构。如果语料是技术文档、API 文档，硬套这套层级切分只会更差。层级切分要做，但层级结构必须来自**你选择的语料**本身。

2. **不要照搬对标项目的量化数字。**
   `Hit@1 89.4%`、`MRR@5 0.911`、`71.7%` 都是**特定语料 + 特定标注集**下的结果，换个语料完全不一样。你要做的是**自己的标注集 + 自己的基线 + 自己的提升**。有真实方法论远比有漂亮数字重要——而且面试官一定会追问「评测集怎么建的」。

3. **没有评测集就不要做检索调优。**
   否则你不知道改动是变好还是变坏，纯属碰运气。

4. **没有 workspace 隔离和路径校验，就不要给 Agent 开放写权限。**
   顺序不能颠倒。这是本项目唯一的**真实安全风险点**。

5. **不要在 Mock 模式下宣称任何能力。**
   Mock 只验证「流程能跑通」，不验证「质量好不好」。Mock 模式的定位是开发调试与 CI，不是效果演示。

6. **不要为了美化指标而把评测集答案泄露进 Prompt。**
   评测集与检索链路必须完全隔离。

7. **不要跳过阶段顺序。**
   阶段 4 强依赖阶段 3，阶段 2 强依赖阶段 1。跳步的结果通常是返工。

8. **不要为了对标而引入不必要的依赖。**
   Milvus 只有语料规模到**万级 chunk 以上**才有意义；当前 51 个 chunk 用 ChromaDB 完全够。
   同理，LlamaIndex 只在**需要 AutoMerging / 层级 node parser** 时才值得引入。

## 6. 关键决策记录（ADR）

> 记录「为什么这么选」，避免后续 AI 反复推翻已有决策。

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | Embedding 默认用**本地哈希向量** | DeepSeek 官方**没有 embedding 接口**。本地哈希向量零依赖、可离线、确定性可复现。**代价**：本质是字面匹配的量化版，没有语义泛化能力——这是当前 RAG 最大的能力边界 |
| D2 | Worker 目前**不提供任何工具** | 在没有 workspace 隔离与路径校验之前开放写权限有真实风险。当前策略是「明确宣告没有工具」，并在 Manager 的 Prompt 里禁止拆出需要工具的子任务 |
| D3 | 依赖失败时 **Worker 与 Checker 双双短路** | 前置失败后输入没有变化，重试必然产出同样的「无法完成」。实测这一条节省了 20 次以上无效调用 |
| D4 | 保留**离线 Mock 模式** | 让 CI 不需要真实 Key，让开发调试零成本。这也是排查随机性问题的有效手段 |
| D5 | `chromadb` 版本约束放宽为 `>=0.5.23` | 0.5.x 在 Windows + Python 3.12 上需要本地编译 `chroma-hnswlib`（缺 MSVC 会失败）；1.x 提供预编译 wheel，两代 API 均已适配 |
| D6 | 混合检索用 **RRF** 而非加权求和 | BM25 分数无上界、余弦相似度固定在 `[-1,1]`，直接加权必须先归一化，而归一化方式会显著影响排序、难以调参。RRF 只用名次，免疫量纲 |
| D7 | 状态机用 **LangGraph** 而非手写循环 | 真正的收益是 `checkpointer`（每个节点边界自动落盘，断点续跑零成本）与 `stream_mode="updates"`（节点级流式）。4 节点的线性图用手写循环也能实现，但断点续跑的正确性很难自己保证 |
| D8 | 保留 **LangChain** 作为模型适配层 | 客观说这一层很薄（只用到 `ChatOpenAI` + 消息类型）。保留的理由是后续接入其它模型厂商成本更低。**如果确定只对接 DeepSeek，换成官方 `openai` SDK 能砍掉一批传递依赖** |
| D9 | 对标项目用 LlamaIndex + Milvus，本项目用 LangChain + ChromaDB | **不强行对齐**。是否引入 LlamaIndex 取决于阶段 3 是否需要 AutoMerging 与层级 node parser；是否引入 Milvus 取决于语料规模（见约束 8） |

### 最终目标态（全部完成后的样子）

- 一个复杂长任务丢进来，系统能**自主规划成 DAG**，**并行调度**无依赖的子任务
- 每个子任务由**合适的角色**执行（写代码的写代码、测试的测试），工具调用**全部受约束**
- 执行结果经过**真实门禁**（测试 + lint）与**LLM 验收**双重检查才算通过
- 全过程**可中断、可恢复**，多个任务**互不干扰**
- 长任务的上下文被主动压缩，成本可控
- 最终产出一个**经过验证的、可交付的结果**，而不只是一段文本

## 附录 · 术语表

| 术语 | 含义 |
| --- | --- |
| **DAG** | 有向无环图。用拓扑依赖描述子任务之间的执行顺序 |
| **RRF** | Reciprocal Rank Fusion，倒数排名融合。`score(d) = Σ 1/(k + rank_i(d))` |
| **AutoMerging** | 层级检索策略。命中叶节点后自动向上合并父节点，返回语义更完整的上下文 |
| **Cross-Encoder Rerank** | 用交叉编码器对召回结果做精排，比向量相似度更准但更慢，因此只用于少量候选 |
| **Chunk** | 文档切分后的最小检索单元 |
| **Leaf chunk** | 层级切分中最底层的片段（叶节点） |
| **Checkpoint** | 状态快照。LangGraph 在每个节点边界自动写入，是断点续跑的基础 |
| **thread_id** | 会话标识，用于隔离不同任务的状态 |
| **workspace** | 单个任务独占的工作目录，Agent 的文件操作被限制在里面 |
| **MCP** | Model Context Protocol，用于标准化地接入外部工具 |
| **Snowball / COLLATOR** | 后台任务调度器，按任务长度与难度分级派发，并负责上下文压缩 |
| **门禁（Gate）** | 进入下一阶段前必须通过的检查，例如 lint、测试 |
