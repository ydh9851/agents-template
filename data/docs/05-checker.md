# Checker Agent：质量验收

Checker 是独立于 Worker 的第二个判断者，它只看两样东西：验收标准和实际产出。

## 判定原则

- 只有结果明确满足验收标准、且没有明显缺漏时才判定通过；
- 缺少关键内容、答非所问、与验收标准不符，一律判定不通过；
- `reason` 必须具体：通过要说依据，不通过要指出缺什么、该怎么补。

判定结果是一个 JSON：`{"pass": true, "reason": "判定理由"}`。

## 状态推进逻辑

Checker 节点不只是判定，它还负责推进状态：

- **通过**：结果写入 `results`，`current_index + 1`，清空 `current_result`；
- **不通过且未超限**：`retries[id]` 累加，`current_index` 保持不变，路由函数会把流程送回 Worker；
- **不通过且超过上限**：该子任务以 `passed=false` 入库，`current_index + 1` 继续下一个。

第三种情况是刻意设计的：单个子任务失败不应该让整个任务失败，最终由 Manager 在汇总时统一提示。

## 依赖失败时的短路

Checker 在调用模型之前，会先检查当前子任务的 `deps` 里有没有**已验收但未通过**的依赖：

- 如果有，直接标记该子任务为未通过（`reason` 写明「依赖子任务未通过验收，缺少有效输入，跳过执行」），`current_index + 1` 继续下一个；
- 不调用模型，也不重试。

原因是输入并没有变化：前置子任务失败了，后续子任务必然只能产出「无法完成」的声明，重试几次结果都一样，纯属浪费 token。Worker 侧有对应的短路逻辑（不调用模型直接返回阻塞说明），两边配合可以将整条失败依赖链的开销降到零次模型调用。

## 异常兜底

如果 Checker 调用模型失败或返回的 JSON 无法解析，代码会**自动放行**并记录「判定异常，自动放行」。这是一条安全底线：宁可放过一个瑕疵结果，也不能让整个任务卡在验收环节。

## 如何提高验收质量

在 `acceptance` 里写可判定的标准，例如「至少列出 3 条关键信息」而不是「内容要好」。标准越可判定，Checker 的判定越稳定。
