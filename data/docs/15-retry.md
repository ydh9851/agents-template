# 重试与失败处理

框架里存在三层不同性质的重试，它们的目的和参数都不同。

## 一、Checker 打回重做（业务级重试）

这是最核心的一层。Worker 产出被 Checker 判定不达标时，`current_index` 不变，条件边把流程送回 Worker，并把上一轮的验收意见一起喂回去。

- 计数方式：`retries[subtask_id]`；
- 上限：`MAX_RETRY_PER_SUBTASK`，默认 2；
- 超限行为：该子任务以 `passed=false` 入库，流程继续下一个，最终状态标记为 `partial`。

**为什么不用无限重试？** 无上限重试在大模型场景下极易形成「打回 → 换个说法 → 还是不合格」的死循环，既浪费成本又永远无法结束任务。

## 二、HTTP 层重试（网络级重试）

`ChatOpenAI` 配置了 `max_retries=2`，处理的是网络抖动、限流等瞬时故障。它和业务级重试完全独立。

## 三、依赖失败短路（不做重试）

如果某个子任务的依赖子任务已经验收失败，那么当前子任务缺少有效输入，重试没有任何意义。此时：

1. Worker 不调用模型，直接返回「阻塞」说明；
2. Checker 也不调用模型，直接标记为未通过并推进下标。

两边都被跳过，一次模型调用都不会发生。这解决的是「一处失败拖垮整条依赖链」的问题——没有这段逻辑时，一个前置子任务失败会导致后续每个子任务各重试 3 轮，全部产出同样的「无法完成」，实测浪费约 20 次以上调用。

## 四、检索降级（非重试的容错）

混合检索失败时不重试，直接在日志里告警并返回空列表。原因是检索是增强项而不是必需项：没有资料 Worker 依然能基于自身知识作答，但整条链路不能因为向量库临时异常而中断。

## Checker 异常时的放行策略

如果 Checker 自身调用失败或输出的 JSON 无法解析，代码会**自动放行**（`pass=true`）并写明「判定异常，自动放行」。

这是一个明确的取舍：验收环节宁可放过一个有瑕疵的结果，也不能让整个任务永久卡死。日志里会留下完整记录，便于事后复查。

## 可观测性建议

`logs` 字段按时间顺序记录了每次拆解、执行、判定和打回，是排查重试问题最直接的入口。`results[].attempts` 则能快速看出哪个子任务反复返工——那通常意味着它的 `acceptance` 写得不够清楚。
