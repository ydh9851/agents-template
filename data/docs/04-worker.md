# Worker Agent：子任务执行

Worker 是唯一真正「干活」的节点，它的输入由四部分组成。

## 输入构成

1. **当前子任务**：id、标题、描述、验收标准；
2. **依赖结果**：`deps` 里各子任务已经通过验收的输出，让 Worker 能接着往下做；
3. **上一轮验收意见**：如果这个子任务是被打回重做的，把 Checker 的意见一并喂回去，避免它重复犯错；
4. **检索资料**：混合检索召回的 top_k 片段，带 `[1] [2]` 编号。

## 调用 RAG 的时机

只有当子任务的 `need_rag` 为 true 时才检索，查询语句是「标题 + 描述」的拼接。检索失败不会中断任务，只会在日志里告警并降级为「无资料」——检索是增强项，不该成为单点故障。

## 输出格式约束

Prompt 里强制了三段式输出：

- **结论**：一句话给出产出；
- **依据与步骤**：分点说明，引用资料时标注编号；
- **自检**：一行说明是否满足验收标准。

这样 Checker 拿到的结果结构稳定，判定准确率明显高于自由格式输出。

## 依赖失败时的短路

Worker 在调用模型之前会先检查 `deps`：如果任一依赖子任务已验收失败，就不调用模型，直接返回一条「【阻塞】依赖子任务 X 未通过验收，缺少可用的输入依据，本子任务不执行，以免编造内容」。

这条短路的价值在于省掉无效调用——输入没有变化时，模型每次都会给出同样的「无法完成」。检测逻辑实现在 `graph/state.py` 的 `failed_deps()`，Worker 与 Checker 共用。

同时 Prompt 也要求：完成子任务所必需的资料完全缺失时，不要编造内容，直接写明阻塞原因与需要补充什么。

## 重试行为

被 Checker 打回后，Worker 会带着「上一轮验收意见」重新执行，`retries` 里记录该子任务的尝试次数，超过 `MAX_RETRY_PER_SUBTASK`（默认 2）就由 Checker 标记失败并继续，避免整图死循环。
