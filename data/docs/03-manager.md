# Manager Agent：任务拆解与结果汇总

Manager 承担两个职责，分别对应状态机的入口节点和出口节点。

## 一、任务拆解（manager_node）

调用大模型，要求它输出严格 JSON：

```json
{"subtasks":[{"id":"t1","title":"标题","description":"做什么","deps":[],"acceptance":"验收标准","need_rag":true}]}
```

拆解的原则：

1. 边界清晰，一个子任务能由一个 Worker 独立完成；
2. 依赖用 `deps` 表达，只能引用前面已定义的 id；
3. 必须有可判定的 `acceptance`，否则 Checker 无法验收；
4. 只保留必要的依赖，能独立完成的子任务不要写成串行依赖；
5. 拆解粒度要克制，不要为凑数量把简单任务拆成多步。

## 系统能力边界（重要）

Worker 是纯语言模型，**没有任何工具**：不能访问文件系统、不能读写代码仓库、不能执行命令、不能联网。它唯一能获得的外部信息是系统自动注入的检索资料。

因此 Manager 被明确约束：

- 禁止拆出「扫描仓库 / 读取源码 / 给出真实文件路径或行号 / 运行代码验证」这类需要工具的子任务；
- 每条 `acceptance` 必须在「不访问文件系统、不执行代码」的前提下可判定；
- 除非子任务是纯写作、汇总或常识推理，否则 `need_rag` 设为 `true`。

违反这条边界的直接后果是：验收标准永远无法达成，子任务会耗尽全部重试次数后失败。这是一个在真实模型上实测踩过的坑——早期版本里 Manager 生成了「给出真实文件路径清单」和「引用具体代码位置」的验收标准，导致 5 个子任务各重试 3 次全部失败。

## 二、输出清洗（normalize_subtasks）

模型输出不可全信，所以落地前统一清洗：

- `id` 去重，重复的自动加后缀，避免 `retries` 字典互相覆盖；
- `deps` 过滤掉未定义或指向自身的引用；
- 数量超过 `MAX_SUBTASKS`（默认 5）时截断，防止任务爆炸；
- 缺失的 `acceptance` 补默认值。

## 三、结果汇总（summarize_node）

把所有子任务结果按「任务背景 → 核心结论 → 关键要点 → 风险与待确认」组织。如果有子任务未通过验收，会在「风险与待确认」里显式列出，最终状态标记为 `partial` 而不是 `finished`，前端据此提示用户。

## 常见问题

**拆得太碎怎么办？** 调小 `MAX_SUBTASKS`，并在 manager.txt 里强化「边界清晰、可独立完成」的要求。

**拆得不对怎么办？** Manager 没有引入 history，目前是一次性拆解。如果需要多轮澄清，可以在 Prompt 里加入用户补充信息。
